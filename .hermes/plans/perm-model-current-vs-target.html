Why it was confusing

  • 3 code paths compute permissions differently
  • jwt.strategy ignores default/denied entirely
  • jwt.strategy is the one that runs on every request
  • role_menu_access was a 4th, barely-used system
  • permissions catalog has 10 rows that don't match the ~90 real keys

How defaultPermissions works

  • Role owns a list of permission keys
  • e.g. OWNER: menu.pos, action.pos.create, ...
  • Anyone assigned that role inherits the whole list
  • Keys live in code (static catalog), not DB
  • SUPERADMIN bypasses all checks regardless

How deniedPermissions works

  • Per-assignment (UserBranch) subtractive list
  • Admin can only REMOVE from role's defaults
  • Can never add beyond role defaults
  • e.g. HS role minus finance.* for branch B
  • Effective = defaults − denied, applied at login & every request
